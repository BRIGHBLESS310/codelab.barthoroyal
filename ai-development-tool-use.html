Constrain model-directed tools

Some systems let a model request an application function, such as searching a catalog or drafting a calendar event. The application—not the model—must authorize and execute that function.

Key idea

Expose only narrow, allowlisted operations. Validate arguments and the current user's permissions; require confirmation before consequential or irreversible actions.

Keep tools constrained and permissioned

Tool use lets a model request a defined application action, such as searching approved records or calculating a value. The model can propose which tool and arguments to use, but trusted code should validate the request and perform the action under the user's permissions.

Expose only the minimum tools needed, use strict argument schemas, and treat retrieved or user-supplied content as untrusted. A tool call can have side effects, so distinguish read-only operations from actions that change data or communicate externally. Require confirmation or human review for consequential changes.

Set time, scope, and resource limits, and log decisions in a way that protects private content. Never rely on the model to enforce authorization or to decide whether it may access a record. This separation limits both accidental misuse and the impact of malicious instructions in input data.

Example

The tool creates a draft and checks authorization before acting. Confirmation keeps the user in control of a change that affects their account.

if request.name == "draft_reminder":
    args = validate_reminder_args(request.arguments)
    require_permission(current_user, "reminders:create")
    return show_confirmation(args)

# Execute only after the user confirms.

Practice
