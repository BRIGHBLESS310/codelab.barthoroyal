Plan for timeouts and uncertainty

Model services can be slow, unavailable, rate-limited, or uncertain. A reliable feature sets deadlines, handles errors explicitly, and gives users a useful alternative rather than hanging or inventing a result.

Key idea

Use bounded retries only where safe, prevent duplicate side effects, and monitor failure rates. Make uncertainty visible and provide a human or non-AI path for important tasks.

Design for failures as normal outcomes

Model calls depend on networks and external services, so they can time out, be rate-limited, or return malformed output. Set a bounded timeout and define a useful fallback, such as offering a manual path or explaining that the feature is temporarily unavailable.

Retries can help with transient errors but may multiply cost or repeat side effects. Retry only appropriate failures, use backoff and limits, and make actions idempotent where possible. Do not repeatedly submit a request that has already caused an external change.

Model output itself is uncertain even when the API succeeds. Validate it, communicate uncertainty honestly, and avoid presenting unsupported content as authoritative. Track latency, failure rate, and quality signals so teams can distinguish an outage from a gradual change in model behavior.

Example

The example distinguishes timeout, outage, and low confidence. Each has a clear user-facing fallback instead of returning an empty or fabricated answer.

try:
    result = await call_model(timeout=15)
except TimeoutError:
    return show_search_instead()
except ServiceUnavailable:
    return explain_temporary_issue()

if result.confidence_is_insufficient:
    return offer_human_help()

Practice

List three failure modes for your project and write the exact user-facing fallback for each. Include how the user can continue without AI.

Try the example, change one detail, and explain how the result changes.
