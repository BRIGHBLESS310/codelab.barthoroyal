Extract repeated patterns

Utilities can make one-off UI clear, but repeating long class strings can make changes inconsistent. In a component framework, extract a component when the pattern has a stable meaning, structure, or behavior.

Key idea

Prefer components with useful semantic names and explicit variants. Avoid a generic abstraction that hides simple markup without removing meaningful duplication.

Reuse the pattern at the right boundary

Repeated utility sequences often represent a component: a button, alert, or card has a stable structure and appearance that should change consistently. In a component-based framework, place those classes in the component so callers reuse behavior and presentation instead of copying markup.

Not every repeated class list requires abstraction. Extract a component when the pattern has a meaningful name, repeated behavior, or likely shared changes. A premature abstraction can make simple differences hard to express; a copied pattern can drift when the same design is updated in several places.

Keep content and state flexible through clear properties or variants, and ensure the component preserves semantic HTML and accessible interaction. This connects utility-first styling to normal component design: utilities define the details, while the component gives the recurring pattern a stable interface.

Example

This React example turns a repeated button pattern into a named component. The component can later accept explicit props for disabled state or a deliberate visual variant.

function PrimaryButton({ children }) {
  return (
    <button className="rounded bg-indigo-600 px-4 py-2 font-semibold text-white hover:bg-indigo-700">
      {children}
    </button>
  );
}

Practice

Find two repeated UI patterns in a sample page. Extract one into a component and decide which differences should be props and which should remain separate.

Try the example, change one detail, and explain how the result changes.
