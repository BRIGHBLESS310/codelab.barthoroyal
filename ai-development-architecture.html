Separate interface, service, and model

A simple architecture keeps the user interface separate from trusted server logic and external model services. The server can apply access checks, minimize data, enforce limits, and validate responses.

Key idea

Do not let a client directly control privileged tools or choose arbitrary upstream resources. Define narrow endpoints and authorization rules for each capability.

Separate responsibilities at trust boundaries

A typical feature has an interface that collects user intent, a service that enforces application rules, and a model integration that handles inference. The service can check permissions, minimize inputs, shape prompts, and validate results before anything reaches the user.

This separation makes failures easier to handle: the interface can present a safe fallback, while the service records operational metrics without exposing unnecessary content. It also makes model providers easier to change and helps keep API credentials away from client-side code.

Do not let the model become the authority for access control, business rules, or safety checks. Enforce those deterministically in trusted application code. Clear boundaries also support focused testing: test the service contract, the model behavior, and the full user journey separately.

Example

The server is the control point for policy and integration. The browser receives only the data needed for the interaction, not secrets or unrestricted service access.

Browser UI -> authenticated app endpoint
App endpoint -> validate request and permissions
App endpoint -> model or retrieval service
App endpoint -> validate result -> UI
