Indexes and Query Practice

Indexes can speed up searches and joins but use storage and add work to writes. Choose them for real query patterns and compare query plans; an index is not automatically beneficial.

In this lesson: Read the explanation, follow the example, and try the practice prompt before continuing.

Explanation

An index is an auxiliary structure that helps an engine find rows without scanning an entire table. It can improve selective filters, joins, and ordering, but it consumes storage and must be maintained as data changes.

A composite index orders values by its column sequence. An index on customer_id then order_date can support searches by customer and date, but may not help a query filtering only on the second column.

Use EXPLAIN or the engine's plan tool to see whether an index is used. Tiny tables, low-selectivity columns, and write-heavy workloads may not benefit; avoid adding indexes speculatively or duplicating existing ones.

The example proposes an index for finding a customer's orders in date order. Compare plans with representative data and measure reads and writes; an index is a trade-off, not a universal speed switch.

Example

CREATE INDEX idx_orders_customer_date
ON orders (customer_id, order_date);

SELECT order_id, order_date
FROM orders
WHERE customer_id = 12
ORDER BY order_date;

Practice

Choose a frequent filter or join, propose an index, then inspect the query plan before and after.
