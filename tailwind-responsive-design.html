Adapt from small screens upward

Tailwind's responsive variants apply utilities at and above configured breakpoints. Unprefixed classes define the base layout; prefixes such as sm: and lg: override or add styles for larger screens.

Key idea

Design the narrow layout first, then add only the breakpoint changes that the content needs. Breakpoints are minimum widths, not device labels.

Breakpoints are minimum-width conditions

In Tailwind's mobile-first model, an unprefixed utility supplies the base style, and a breakpoint prefix such as md: applies an override at that minimum viewport width and above. It does not mean “tablet only.” For example, grid-cols-1 md:grid-cols-2 changes from one to two columns at the breakpoint and keeps two columns on wider screens unless another rule overrides it.

Start with the narrow layout because constrained space exposes content-order and overflow problems early. Add a breakpoint when the design genuinely needs a change—not simply because a device category exists. Breakpoints are tools for responding to available space, not labels for specific phones or tablets.

Test the transitions as well as the endpoints. Long words, translated text, and controls can overflow between familiar device widths. Responsive layout should preserve readable line lengths, touch-friendly controls, and a sensible reading order at every width.

Example

The page is a single column by default. From the medium breakpoint, it becomes a two-column grid with a wider article and a sidebar.

<section class="grid grid-cols-1 gap-6 p-4 md:grid-cols-[minmax(0,2fr)_minmax(14rem,1fr)] md:p-8">
  <article>Primary article content</article>
  <aside>Related links</aside>
</section>

Practice

Create a page that stacks a main article and a related-links panel on a phone, then places them side by side when there is room. Check for horizontal overflow.

Try the example, change one detail, and explain how the result changes.
