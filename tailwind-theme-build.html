Keep a consistent theme and build

A design system uses shared choices for colors, spacing, and typography. Tailwind theme customization and CSS entry-point conventions vary by major version, so use the documentation matching the project rather than mixing configuration examples.

Key idea

Use a production build to verify that the scanner includes all relevant template files. Keep class names discoverable as complete strings and avoid shipping development-only configuration or secrets.

Connect design tokens to the production build

A theme centralizes recurring design decisions—such as brand colors, font families, spacing, and breakpoints—so components can use meaningful shared values. Tailwind's mechanism for declaring theme values differs between major versions, so use the documentation that matches the installed package rather than mixing configuration styles.

In production, the build scans application sources and emits a stylesheet containing the utilities it discovers. Keep class names statically detectable; constructing fragments such as text- plus a runtime color can prevent the scanner from seeing the complete candidate. Prefer explicit mappings or a documented safelist strategy when dynamic choices are necessary.

Validate a production build, not only the development server. Production settings may scan different paths, minify CSS, or omit unexpected files. A consistent theme and verified build reduce visual drift and prevent styles that worked locally from disappearing after deployment.
