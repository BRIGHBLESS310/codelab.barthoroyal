Style interaction states accessibly

State variants such as hover:, focus:, active:, and disabled: apply utilities for a particular interaction state. Keyboard users need a clear focus indicator, even when hover styling is present.

Key idea

Do not remove the browser outline without replacing it. Ensure controls communicate disabled state and retain adequate contrast in all states.

Make interaction states perceivable

A state variant scopes a utility to a condition: hover:bg-* changes appearance while a pointing device is over an element, and focus-visible:ring-* can make keyboard focus easy to track. These variants describe when a style applies; they do not add behavior such as navigation or form submission.

Hover is not a substitute for focus. Keyboard users need a clearly visible focus indicator, and touch users may never experience hover. Avoid removing the browser outline unless a replacement remains visible with sufficient contrast against every relevant background.

Choose states that explain the control's affordance—what it does and whether it is available. Disabled, active, and selected states may need separate semantics as well as visual treatments. Native buttons and links provide keyboard behavior and accessibility semantics that styling alone cannot supply.

Example

Hover changes the background, focus-visible draws a keyboard indicator, and disabled styles clarify unavailable interaction. Native button semantics provide keyboard activation.

<button class="rounded bg-indigo-600 px-4 py-2 text-white hover:bg-indigo-700 focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-indigo-600 disabled:cursor-not-allowed disabled:opacity-50">
  Continue
</button>

Practice

Add hover, keyboard focus, and disabled styles to a link and a button. Navigate using only the keyboard and verify each state is easy to see.

Try the example, change one detail, and explain how the result changes.
