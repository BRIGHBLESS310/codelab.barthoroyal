Design prompts as part of the interface

A prompt can specify role, task, context, format, and boundaries. It is application logic and should be versioned and tested rather than improvised only after deployment.

Key idea

Prompts cannot guarantee correct or safe behavior. Avoid including secrets; separate trusted instructions from user-provided content and validate the output independently.

Make the instruction testable

A well-designed prompt specifies the task, trusted context, output expectations, and what to do when evidence is missing. These parts reduce ambiguity and make the model's job narrower. Delimit user content clearly so it is treated as data to process rather than as an instruction that overrides the task.

Prompts are not security controls and cannot guarantee truth. Validate important claims and keep policy enforcement in application code. If output must follow a format, describe that format precisely and use provider-supported structured output when available, followed by local validation.

Version prompts alongside code and test them against representative examples, including adversarially phrased, ambiguous, and unsupported requests. Compare changes on the same evaluation set to see whether one improvement creates regressions elsewhere. This treats prompt design as an engineered interface.

Example

The instruction sets a constrained task and a response shape. A real implementation should use the provider's supported message roles and still verify the returned structure and citations.

instruction = """
Task: answer using only the supplied reference.
If the reference is insufficient, say so.
Return a concise answer and list source titles.
"""
