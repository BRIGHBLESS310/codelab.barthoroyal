Transactions

Transactions group related statements into a unit: COMMIT makes changes durable and ROLLBACK abandons uncommitted changes. This helps keep data consistent when a multi-step operation fails.

In this lesson: Read the explanation, follow the example, and try the practice prompt before continuing.

Explanation

A transaction groups statements into one logical unit. COMMIT makes its changes permanent; ROLLBACK abandons uncommitted changes. This matters when several writes must succeed together, such as debiting one account and crediting another.

Atomicity prevents a partial unit of work, isolation governs how concurrent transactions see one another, and durability concerns committed data surviving failures. Exact isolation levels and locking vary, so boundaries should match the application's needs.

A transaction protects only statements that participate in it, and some engines have special transaction behavior. Keep the transaction brief, roll back on errors, and do not report success until commit succeeds.

The example transfers 25 units between two accounts and commits both updates together. A production transfer should validate the amount, verify affected rows, and use concurrency-safe updates.

Example

BEGIN;
UPDATE accounts SET balance = balance - 25 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 25 WHERE account_id = 2;
COMMIT;

Practice

In a disposable database, make a small change inside a transaction, inspect it, and roll it back.
