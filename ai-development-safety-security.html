Protect the feature and its users

AI features inherit ordinary application risks and add model-specific issues such as untrusted output, prompt injection in retrieved content, and unexpected tool requests. Safety requires layered controls, not just prompt wording.

Key idea

Keep authorization outside model decisions, isolate untrusted content, restrict tools, validate outputs, and test failure cases. Do not place secrets in prompts or retrieved documents.

Model-specific risks need ordinary controls too

AI features can be exposed to prompt injection, abusive inputs, sensitive-data disclosure, and unsafe or misleading outputs. A prompt asking the model to ignore malicious instructions is useful guidance but is not a security boundary. Treat all external text and model output as untrusted input.

Enforce authentication, authorization, input limits, and output handling in application code. Restrict retrieval to documents the user is allowed to see, limit tools and their permissions, and avoid rendering generated text as executable markup. Apply abuse monitoring and rate limits appropriate to the feature.

Test realistic misuse and failure scenarios, including attempts to retrieve restricted material or trigger unauthorized actions. Define escalation and incident-response paths before launch. Security and safety are ongoing properties of the system, not a checklist completed by selecting a capable model.

Example

The model output is checked before use and cannot grant itself access. A fallback handles results that fail policy or format checks.

candidate = model_response(untrusted_input)
validated = validate_format(candidate)

if not allowed_action(validated):
    return safe_fallback()
return present_as_unverified_draft(validated)

Practice
