Validate structured model output

Structured output can make a response easier for an application to process, but a model's JSON-looking text is not automatically valid or trustworthy. Use supported schema features where available and validate on the server.

Key idea

Check required fields, types, allowed values, and size. Treat any returned text as untrusted data; do not execute it or use it to bypass authorization.

Parsing is not the same as validation

Structured output asks a model to return fields in a predictable shape, often JSON. A syntactically valid response can still omit required information, use an unexpected value, or invent content. Parsing only checks whether the representation can be read; it does not establish that the data is complete or correct.

Define a schema with required fields, types, allowed ranges, and enumerated values where appropriate. Validate the response on the server and handle parse failures or schema violations as expected outcomes. Do not silently coerce invalid values into trusted application state.

For consequential fields, check them against trusted source material or ask a person to review them. A schema constrains form, not truth. Keep the original evidence available where permitted so downstream users can understand what a value means and where it came from.

Example

Parsing and checking fields are separate steps. Validation prevents malformed or unexpected content from silently becoming application state.

raw = model_response()
result = parse_json(raw)

if result.get("status") not in {"ready", "needs_review"}:
    raise ValueError("Unexpected status")
if not isinstance(result.get("summary"), str):
    raise ValueError("Summary must be text")

Practice

Define a three-field schema for a meeting summary. List allowed values and one validation failure for each field.

Try the example, change one detail, and explain how the result changes.
